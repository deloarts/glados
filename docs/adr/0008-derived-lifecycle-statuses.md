# 0008 lifecycle statuses are derived from facts and intents by one reconciler

- Status: accepted
- Date: 2026-10-16

## context

Lots, lot positions, production orders, supplier orders, order lines and the demands of the three item families each store a status. Close to a hundred places in the code assigned those statuses, each deciding the target on its own: four copies of the lot rollup, three rule sets for a demand's status, a transition table per status that no writer consulted, and cascades that forgot their neighbours. The statuses drifted from what had actually happened: a held lot could not complete, a canceled line kept its position stuck, a scrap left work open, deliveries were booked on canceled lines, and concurrent requests overwrote each other. Guarding every writer with a transition table would have kept the many writers and their separate decisions. Recomputing the status on every read would have made the lists, filters and the scheduler slow and would have hidden drift instead of fixing it. Capturing changed rows automatically in a session listener would have tied the rule to the ORM and kept it out of reach of the unit-test fakes.

## decision

The status of every core aggregate is a pure function of its recorded facts (quantities, delivery and completion rows, interruptions, allocations) and a few intent timestamps that only a user action sets (held, canceled, force-completed, requested, ordered, fulfilled by hand). The functions live in `src/modules/fulfillment/domain/services/lifecycle/` as ordered decision tables, where the first row that applies wins; a position's kind and completed count and the stamps of a status are derived the same way. Statuses stay stored columns for queries, and only the derivation writes them. A use case records facts and intents, registers what it touched with the `LifecycleReconciler`, and calls it before it commits; the reconciler adds the rows that depend on the touched ones, locks them in one fixed order, recomputes them from fresh reads, writes only what differs with one changelog line per field, and publishes the status events. Users act through intents, which an intent table guards and which the API reports per row as allowed `actions`. Rows carry an optimistic version column. An architecture test forbids status writes outside the derivation, an integration fixture checks every test's database for drift, a property suite exercises random command sequences, and the `lifecycle-drift` and `lifecycle-repair` commands compare and repair a real database.

## consequences

A status always says what the facts say, and a new path cannot forget a neighbour, because the reconciler follows the dependencies itself. The state machine page of the handbook shows the tables the code runs, so it cannot fall behind. Adding a user action means adding an intent with its guard and its fact or timestamp, never a status assignment; the rules for that are in [CONTRIBUTING.md section 3.7](../CONTRIBUTING.md#37-lifecycle-facts-intents-and-the-reconciler). A use case must touch every aggregate whose facts it writes and must take its locks through the request's lock plan before it reads what it checks. Requests lock more rows than before and can answer 409 where they silently overwrote before. Some statuses read differently from earlier versions: an order counts only its live lines, a demand is ordered only when it is fully covered and placed, a held lot still completes, and force-completing a lot closes it short.
